OS Engine: Concurrency & Deadlock Engineering SECTION 04

1. Why Banker's Algorithm Fails Dynamic Airline Reservations

Dijkstra's Banker's Algorithm is an optimal theoretical model for static systems where every process can declare its Maximum Resource Need vector ($\vec{Max}$) at thread spawn. In an airline reservation platform:

  • Passengers interact dynamically: they do not know in advance how many seats, meals, or baggage allowances they will add as they browse the cabin.
  • Declaring a worst-case maximum claim ($\vec{Max} = \text{all 30 seats}$) causes the Banker's safety check to artificially starve other threads, reducing booking throughput by over 80%.

EndureAir's Resolution: We retained Banker's Algorithm in BankersAlgorithm as a formal comparative benchmark (as demonstrated in aryan_os.cpp), but deployed Strict Ascending Lock Ordering and a Wait-For Graph (WFG) for runtime production seat allocations.

2. Strict Ascending Lock Ordering ($O(1)$ Deadlock Elimination)

When a user books multiple seats (e.g., Seat 12 and Seat 04 for a family booking), acquiring locks in random order ($User_A: 12 \to 04$, $User_B: 04 \to 12$) creates an instantaneous circular-wait condition ($User_A \text{ waits for } User_B \text{ and vice-versa}$).

Mathematical Deadlock Guarantee via Total Ordering
By sorting requested seat IDs in strictly ascending order ($Seat_1 < Seat_2 < \dots < Seat_k$) prior to mutex acquisition, circular dependency is mathematically impossible ($\forall (i, j): i < j \implies Lock(Seat_i) \text{ precedes } Lock(Seat_j)$). Runtime lock overhead drops to $O(1)$.

3. Wait-For Graph (WFG) with Depth-First Search (DFS) Cycle Detection

For arbitrary dynamic resources where upfront sorting is impossible, the WaitForGraph maintains a live directed graph where vertices represent active transactions ($T_i$) and directed edges represent lock blocking ($T_i \to T_j \iff T_i \text{ is blocked waiting for a lock held by } T_j$):

  • Detection Algorithm: Uses three-color DFS traversal (White = Unvisited, Gray = Active in recursion stack, Black = Fully explored). A directed cycle exists if and only if an edge leads to a Gray node.
  • Victim Selection: When a cycle is detected, the engine inspects arrival timestamps and aborts the youngest transaction ($T_{\text{victim}}$), rolling back its partial locks to minimize overall wasted computation.

4. Starvation-Free Priority Queue with Monotonic Aging

To prevent low-priority Economy booking requests from indefinitely starving behind VIP/First-Class reservations, the scheduler runs a priority queue with dynamic aging:

$$\text{Effective Priority} = \text{Base Priority} + (\Delta t \times \text{Aging Bonus})$$

Every scheduling tick without allocation increments $\text{Aging Bonus}$, monotonically elevating the request until it reaches the head of the dispatch queue, guaranteeing bounded waiting time for all passengers.

DBMS Engine: Crash Consistency & Invariants SECTION 05

1. The Distributed Inconsistency Hazard

In any real-world commercial reservation platform, booking a seat spans two non-atomic systems: an external payment gateway (Credit Card / Stripe / Bank) and an internal database transaction (MySQL). Consider the catastrophic crash sequence: 

[User] ----(1. Reserve Seat #04)----> [Application Engine]
                                              |
                                     (2. Lock Seat in HELD state)
                                              |
[Credit Card Gateway] <---(3. Deduct $450)----+
         |
  (Card Charged OK)
         |
         x ------> [SERVER PROCESS KILLED BY POWER FAILURE / SIGKILL HERE]
                                              |
[Database: Seat never confirmed! User was charged $450 with NO ticket!]

2. Application-Level Write-Ahead Logging (`wal.log`)

To eliminate this financial disaster, EndureAir implements an application-level journal (BookingJournal) that strictly adheres to the Write-Ahead Logging Rule: no external payment call or database mutation may occur until a log record is flushed to persistent storage.

Journal Step Persisted Fields State Guarantees Provided
HOLD_CREATED txnId, idemKey, seatNo, holdTTL Records temporary 60-second lease with CAS version number.
PAYMENT_REQ txnId, idemKey, amount, gatewayId Written immediately before dispatching the HTTP call to the payment gateway.
PAYMENT_CONF txnId, idemKey, paymentRef, amount Written the instant payment gateway returns success.
BOOKING_CONF txnId, idemKey, seatNo, ticketId Written when MySQL marks seat as BOOKED and passenger name is recorded.
CHECKPOINT activeTxnList, lastFlushedId Flushes dirty memory buffers to disk, bounding recovery scan time.

3. The Autonomous Cross-System Reconciler

Upon reboot (or during background reconciliation), the ReconciliationEngine parses wal.log and executes a dual-branch repair protocol:

  • Branch A (Safe Commitment): If PAYMENT_CONFIRMED exists in the log and the seat hold has not expired, the reconciler transitions the seat to BOOKED and creates the passenger ticket without requiring the user to re-pay.
  • Branch B (Compensating Refund): If the seat hold expired during downtime and was subsequently booked by another passenger, the reconciler triggers an automated Compensating Refund against the payment gateway, logs the event to reconciliation_audit, and informs the passenger.

4. The 4 Mathematical Consistency Invariants

The system includes an automated invariant verification engine (assertInvariantReport()) that validates all four invariants on every test run:

The Four Verified Invariants
  1. Invariant 1 (Financial Conservation): $\forall \text{ Payment } P \in \text{Ledger}: P.\text{status} = \text{CHARGED} \iff (\exists ! \text{ Booking } B: B.\text{paymentId} = P.\text{id}) \lor (\exists ! \text{ Refund } R: R.\text{paymentId} = P.\text{id})$.
  2. Invariant 2 (Mutual Exclusion): $\forall \text{ Seat } S \in \text{Seats}: \text{Count}(\text{ActiveBookings}(S)) \le 1$. Double-booking is mathematically impossible.
  3. Invariant 3 (Clean Eviction): $\forall \text{ Seat } S \text{ where } S.\text{status} = \text{HELD}: \text{CurrentTime}() \le S.\text{holdExpiresAt}$. No hold remains stuck past 60s TTL.
  4. Invariant 4 (Payment Idempotency): $\forall \text{ IdempotencyKey } K: \text{Count}(\text{Charges}(K)) \le 1$. Retrying requests never triggers duplicate charges.

Comprehensive Viva Defense Kit SECTION 07

These 9 core questions cover the exact theoretical and practical topics examiners probe during PBL Phase-III evaluations. Review them thoroughly:

Aryan (OS) Q1: Why did you choose Lock Ordering and WFG instead of relying solely on Banker's Algorithm?
Model Answer: “Banker's Algorithm is a deadlock avoidance technique that requires knowing each process's maximum resource vector ($\vec{Max}$) at the time of creation. In airline reservations, customers dynamically add seats, baggage, and upgrades; they cannot declare their maximum demand in advance. Declaring a worst-case claim would starve the entire system. Instead, we implemented Strict Ascending Lock Ordering ($Seat_1 < Seat_2 < \dots < Seat_k$), which mathematically eliminates the circular-wait condition in $O(1)$ time. We complemented this with a Wait-For Graph (WFG) using three-color DFS cycle detection and youngest-victim rollback, keeping Banker's Algorithm as a comparative study in aryan_os.cpp.”
Aryan (OS) Q2: How does your system prevent starvation for low-priority booking requests?
Model Answer: “We implemented a Priority Queue with Dynamic Aging in aryan_os.cpp. Each booking request has a base priority (1 to 10). Every scheduling tick that an unallocated request spends waiting in the ready queue, its aging bonus is incremented. Eventually, its effective priority surpasses higher-base-priority incoming requests, guaranteeing bounded waiting time and mathematical starvation prevention.”
Aryan (OS) Q3: How do you simulate realistic system crashes to test your recovery logic?
Model Answer: “We built an automated Crash Injection Harness with 5 named fail points: FP_AFTER_HOLD, FP_AFTER_PAYMENT, FP_BEFORE_CONFIRM, and FP_MID_RECONCILE. In sub-process testing (crash_test_runner.bat), the harness triggers an abrupt OS kill using _exit(137) (the Windows equivalent of SIGKILL), bypassing C++ destructors and runtime cleanup to simulate sudden power loss.”
Bijendra (DBMS) Q4: How does your system guarantee that a seat can never be double-booked?
Model Answer: “Double-booking is prevented through three concentric layers: First, at the OS level, each seat has a fine-grained mutex. Second, the seat lifecycle follows a Two-Phase State Machine: AVAILABLE $\to$ HELD (with a 60-second TTL and Compare-And-Swap version counter) $\to$ BOOKED. Third, at the database tier, we enforce atomic SELECT ... FOR UPDATE row-level locks and a unique composite SQL constraint on (flight_id, seat_number) in MySQL 8.0.”
Bijendra (DBMS) Q5: If the database already has its own WAL (InnoDB redo log), why did you build an Application-level WAL?
Model Answer: “The MySQL InnoDB redo log only guarantees ACID properties inside the database. It has no visibility into external distributed entities, such as the third-party payment gateway. If the card is charged successfully, but the server crashes before sending the SQL commit, MySQL rolls back its internal state—leaving the passenger charged with no ticket. Our Application WAL (wal.log) logs the payment gateway authorization before initiating the database transaction, allowing our Autonomous Reconciler to detect orphaned charges upon reboot and issue safe commits or compensating refunds.”
Bijendra (DBMS) Q6: What is a Compensating Refund and when is it executed?
Model Answer: “A Compensating Refund is an inverse transaction that neutralizes an orphaned distributed operation. If the server crashed after charging a user's card, and during the downtime the 60-second seat hold expired and the seat was booked by another passenger, the reconciler cannot safely book the original seat. It immediately executes a compensating refund, records the action in reconciliation_audit, and restores invariant 1 (Financial Conservation).”
Yash (Fullstack) Q7: How did you optimize the 3D WebGL scrollytelling to maintain 60+ FPS without lagging?
Model Answer: “We performed three major optimizations: First, we removed camera double-lerping by switching from frame-rate dependent easing to damped delta-time interpolation in CameraRig.tsx. Second, we pre-cached all PBR materials in AircraftModel.tsx to prevent WebGL shader recompilations during scrolling. Third, we replaced SVG feTurbulence filter effects with lightweight CSS noise grain, saving GPU fragment shader overhead. The entire 5-scene voyage runs on a single continuous RequestAnimationFrame loop.”
Yash (Fullstack) Q8: What is your Idempotency strategy and how does it prevent duplicate charges?
Model Answer: “Every booking and payment request is assigned a client-generated UUIDv4 Idempotency Key coupled with a SHA-256 request payload hash. The Node.js gateway checks this key before processing. If a network timeout occurs and the user re-clicks 'Book', the gateway detects the duplicate key in our active transactions table and returns the original cached response without re-executing payment or seat allocation.”
Yash (Fullstack) Q9: What happens if MySQL is not running on the evaluator's computer?
Model Answer: “We engineered an automatic Hybrid In-Memory Fallback in server.js. The server attempts to connect to local MySQL 8.0 on startup. If MySQL is offline or credentials fail, it logs a warning and seamlessly initializes an in-memory 30-seat relational data store that mirrors all schema constraints. This guarantees that the entire 3D web experience, seat selection, and ticket passes run with 100% reliability in any offline evaluation environment.”
